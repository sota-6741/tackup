# Design doc: 台帳・掲示物の編集（ステップ8）

台帳（`/boards/{boardId}/posts`）は、その掲示板の掲示物を、過去のものも含めてすべて並べる管理用の一覧。状態（下書き・掲示開始前・公開中・期限切れ・撤去済み）を付けて出す。
台帳から、掲示物の編集（タイトル・掲示期間・説明文・外部リンク）、原本の差し替え、撤去済みにする操作ができる。
PR は 3 つに分ける（台帳の一覧と撤去 → 編集 → 原本の差し替え）。

根拠: [requirements.md](../requirements.md) の 15・16・17・32・34.3・34.5・34.7・37.8・38.6。画面は [screens.md](../screens.md) の S8。

## 構成

```text
/boards/{boardId}/posts                        /boards/{boardId}/posts/{publicId}/edit
        │                                                   │
 listLedgerPosts（所属を確認）                    getEditablePost（所属を確認）
   PostRepository.findByBoardId                             ▼
        ▼                                             EditPostForm
   PostLedger ──「撤去済みにする」──▶ removePost       ├─ updatePostAction ──▶ updatePost
              ──「編集」──▶ 編集の画面                  └─ replaceOriginalAction ──▶ replaceOriginal
```

## 決めたこと

| 項目 | 決めたこと | 理由 |
| -- | -- | -- |
| 台帳に出す掲示物 | その掲示板のすべての掲示物（状態を問わない） | 要件 16 |
| 状態 | domain の `postDisplayState` で決める（`status` と日時の両方を見る）。台帳と掲示物詳細で同じ関数を使う | 要件 16・32 |
| 並び順 | 掲示開始の新しい順、同じ日時なら ID の大きい順 | 掲示板ボードと同じ並びで、続きの位置の形もそのまま使える。登録日時（DB が振る、マイクロ秒まである値）で並べると、ミリ秒までしか持てない続きの位置と合わず、抜けや重複が出る |
| 索引 | `(board_id, publish_from, id)`。今の `board_id` だけの索引は、これに含まれるのでなくす | 一覧の絞り込みと並び順に合わせる（要件 34.5） |
| 見られる人・操作できる人 | その掲示板のメンバー（admin・poster） | 要件 2 の権限の表 |
| 撤去済みにする | 状態が `published` の行に「撤去済みにする」を出す。ステップ7 の `removePost` をそのまま使う | 無期限の掲示物・期限前の掲示物は、撤去タスクに出ない |
| 編集の URL | `/boards/{boardId}/posts/{publicId}/edit`。要件の `{postId}` には、公開の ID を使う | 内部の ID を画面と URL に出さない方針（掲示物詳細・掲示板ボード）にそろえる |
| 編集できる掲示物 | 撤去済みでないもの（下書き・`published`） | 撤去済みは過去の記録なので、書き換えない |
| 編集できる項目 | タイトル・掲示開始・掲示終了（無期限を含む）・説明文・外部リンク。決まりは登録と同じ domain の関数で確かめる | 要件 17 |
| 同時の編集 | あとから保存したほうで上書きする。撤去済みにされた掲示物への保存は、`status <> 'removed'` を条件にした UPDATE で防ぐ | 編集が重なることは少ない。項目ごとの突き合わせは要らない |
| 原本の差し替え | 登録と同じ流れ（署名付き URL でアップロード → 先頭のバイトと世代を確かめる → 正式な場所へ移す）。移す先は、差し替えのたびに新しいキーにする。DB の行を新しいキーに書き換えたあとで、古いファイルを消す | 要件 17 の「差し替え処理中に既存掲示物が参照不能になる状態を作らない」。同じキーに上書きすると、途中で失敗したときに元のファイルが失われる |
| 差し替えのときの容量の上限 | 掲示板の行をロックしてから、「今の合計 − 古いファイル + 新しいファイル」で確かめる | 要件 34.7。登録と同じやり方 |
| 回数の制限 | 編集と差し替えを、ユーザーごとの書き込みの制限で包む。差し替えのアップロード URL の発行は、登録と同じ制限 | 要件 34.3 |
| 下書き | 台帳には状態を付けて出す。下書きを作る操作は、このステップでは足さない | 要件に下書きを作る操作がない（[post-registration.md](post-registration.md)）。台帳の側は、下書きがあっても正しく出るようにしておく |

## 検討した代替案

| 案 | 却下理由 |
| -- | -- |
| 登録の新しい順に並べる | 上の「並び順」のとおり、続きの位置と合わない。合わせるには、登録日時をミリ秒に丸めて保存する変更が要る |
| 状態で絞り込む | 状態は日時から決まるので、状態ごとに SQL の条件が要る。1 掲示板 500 件までなので、必要になってから足す |
| 編集の画面で、原本の差し替えと項目の編集を 1 回の保存にまとめる | 失敗の種類が混ざり、途中で失敗したときの後始末が増える。差し替えは別の操作にする |
| 差し替えで、同じキーに上書きする | 移すのに失敗すると、元のファイルが失われる。署名付き URL のキャッシュを入れたときに、古い中身が出る |
| 差し替えの履歴（以前の原本）を残す | 要件にない。容量の上限にも数えることになる |

## やらないこと

- 下書きを作る・公開する操作
- 撤去済みを元に戻す操作、掲示物の削除
- 台帳の絞り込み・検索
- 閲覧数の表示（要件 31）
