# Design doc: 掲示物登録（ステップ4）

ブラウザが原本とサムネイルを `pending/` へ直接アップロードし、登録のときにサーバーが中身を確かめて正式な場所へ移してから `Post` を作る。
アップロードのキーに掲示板とユーザーを含め、DB に「アップロード中」の記録を持たずに、発行した相手と結びつける。
PR は 4 つに分ける（テーブルと決まり → ファイルの確認と移動 → 登録の画面 → 回数の制限）。

根拠: [requirements.md](../requirements.md) の 7・8・9・10・26・33・34.2〜34.4・37.4・38.1。画面は [screens.md](../screens.md) の S4。

## 流れ

```text
ブラウザ                              サーバー                        Cloud Storage
原本を選ぶ → サムネイルを作る
createUploadUrlsAction ────────────→ 権限・形式・サイズ・容量を確認
                       ←──────────── 原本とサムネイルの URL とキー
PUT（原本・サムネイル）─────────────────────────────────────────→ pending/{boardId}/{userId}/{uuid}
registerPostAction ────────────────→ 1. 権限、タイトル、掲示期間、キーの形を確認
                                     2. 先頭のバイトと世代を読む ─────→
                                     3. 世代を条件に正式な場所へ移す ──→ boards/{boardId}/posts/{postId}/…
                                     4. 掲示板の行をロックし、上限を確かめて Post を作る
                       ←──────────── /boards/{boardId} へ移動
```

2 で失敗したら `pending/` のファイルを消す。3 で失敗したら、すでに正式な場所へ移したファイルと `pending/` に残ったファイルを消す。4 で失敗したら移したファイルを消す。消し損ねても、`pending/` は 1 日のライフサイクルで消える。正式な場所に残ったファイルは `Post` から参照されないだけで、閲覧はできない。

## 決めたこと

| 項目 | 決めたこと | 理由 |
| -- | -- | -- |
| キーと発行先の結びつけ | キーを `pending/{boardId}/{userId}/{uuid}` にし、登録のときに接頭辞を確かめる | ほかの掲示板・ユーザーのキーで登録できなくなる。DB もストレージの追加の問い合わせも要らない |
| 正式な場所 | `boards/{boardId}/posts/{postId}/original` と `…/thumbnail` | 掲示板ごとの容量の計算と、掲示板の削除のときの掃除が接頭辞でできる。`postId` はサーバーが先に決める |
| ファイルの確認 | 先頭 12 バイトを domain の純粋な関数で判定し、ストレージに記録された `Content-Type` と一致することを確かめる | 要件 8。ライブラリを足さずに 4 形式を見分けられる |
| 登録時のステータス | `published` で登録する | 要件 38.1 の「登録できる」「公開条件を満たせば表示される」を満たす最小の形。下書きを作る操作は要件にない |
| サムネイルの形式 | WebP。書き出せないブラウザでは JPEG（品質 0.8、背景は白）で作り直す。上限 2MB | PNG のままだと写真で数 MB になり、一覧が重くなる。サーバーは WebP と JPEG だけを受け付ける |
| 上限（34.2） | 掲示物 500 件と容量 5GB を、`Post` を作るトランザクションの中で掲示板の行をロックして確かめる。URL の発行時はロックせずに容量だけ確かめる | 発行時の確認は無駄なアップロードを早く止めるためで、守るのは登録時 |
| 容量の計算 | `Post` に原本とサムネイルのサイズを持たせ、合計を SQL で出す | ストレージを数えに行かない（34.4） |
| 日時の入力 | `datetime-local` の値をブラウザで ISO 8601（UTC）に変えて送る。サーバーは `expiresAt > publishFrom` だけを確かめる | タイムゾーンを知っているのはブラウザだけ。過去の日時の登録（貼り出し済みの掲示物の記録）を妨げない |
| 回数の制限（34.3） | Postgres のテーブルに、ユーザーと時間枠ごとの回数を持つ | 複数のインスタンスで共有でき、新しいミドルウェアを足さない |

## 検討した代替案

| 案 | 却下理由 |
| -- | -- |
| 発行したキーを DB のテーブルに記録する | 登録されなかった行の掃除が要る。接頭辞で同じことが確かめられる |
| キーに署名（HMAC）を付けて返す | 秘密の値の管理が増える。接頭辞で足りる |
| ファイルを移さず `pending/` のキーをそのまま `Post` に持たせる | 1 日のライフサイクルを使えず、確認後に差し替えられる（要件 8） |
| `file-type` などのライブラリで形式を判定する | 4 形式の先頭のバイトを見るだけなので、依存を足すほどではない |
| サムネイルが PNG になったらそのまま保存する | 一覧の転送量が増える。要件 34 の「サムネイルを利用する」意味が薄れる |
| 回数の制限を Redis（Memorystore）で数える | 常時動くインスタンスの費用と VPC の設定が要る。この規模では Postgres で足りる |

## PR の分け方

| # | 内容 | 主な確認 |
| -- | -- | -- |
| 1 | `Post` のテーブル、domain の決まり（タイトル・掲示期間・形式の判定・サムネイル）、`PostRepository` | ユニットテスト、`*.db.test.ts` |
| 2 | `FileStorage` に先頭の読み取り・世代を条件にした移動・削除を足す。キーの形を変え、サムネイルの URL も発行する。`pending/` のライフサイクル | `*.storage.test.ts`、`*.gcs.test.ts` |
| 3 | `registerPost`、Server Action、登録のフォーム、掲示板ボードからの導線、上限 | ユニットテスト、ブラウザテスト、e2e |
| 4 | アップロード URL の発行と書き込みの操作の回数の制限 | ユニットテスト、`*.db.test.ts` |

## やらないこと

- 下書きの保存、掲示物の編集・原本の差し替え（要件 17。台帳のステップ）
- 説明文・外部 URL の入力。列だけ用意し、入力は掲示物詳細のステップで足す
- 掲示板ボードでの掲示物の表示（ステップ5）
- 登録されなかった正式な場所のファイルを探して消す仕組み
