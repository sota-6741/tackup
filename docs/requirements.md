# Requirements

# 1. 目的

本システムは、掲示物の登録から掲示、期限管理、撤去、履歴管理までを一貫して扱うための掲示物管理システムである。

特に、掲示期間を過ぎた掲示物を自動的に公開対象から外し、物理掲示物の撤去対象として管理できることを重視する。

本システムでは、以下のライフサイクルを成立させる。

```text
登録
 ↓
掲示
 ↓
期限到来
 ↓
公開終了
 ↓
撤去対象化
 ↓
撤去
 ↓
履歴保存
```

---

# 2. システム概要

本システムでは、管理者・掲示者がPDFまたは画像形式の掲示物を登録し、掲示期間を設定する。

登録された掲示物は掲示板上で公開され、設定された期限を過ぎると自動的に一般閲覧対象から除外される。

期限切れとなった掲示物は撤去タスクとして管理され、実際の物理掲示物を撤去した後に撤去済みとして記録する。

過去の掲示物については台帳から履歴を確認できる。

ログインユーザーは掲示板を作成し、メンバーを登録して掲示板を運用する。

掲示板は公開（public）または非公開（private）のいずれかとする。

一般閲覧者は、公開掲示板についてのみ、招待リンクまたは掲示物に付与されたQRコードを経由して掲示物を閲覧する。非公開掲示板はメンバーのみ閲覧できる。

# 4. ユーザー

## 4.1 ログインユーザー

Googleアカウントを利用してログインする。

ログインユーザーは掲示板を作成できる。作成者はその掲示板の admin になる。

ログインユーザーは、自身が所属する掲示板についてロールに応じて以下の操作を行える（詳細は「5. ロール」）。

* 掲示物の登録
* 掲示物の編集
* 掲示物の差し替え
* 掲示物の公開
* 掲示物の撤去
* 撤去タスクの確認
* 台帳の閲覧
* 招待リンクの表示・再発行
* 掲示板の編集（公開設定を含む）・削除
* メンバーの追加・ロール変更・削除

---

## 4.2 一般閲覧者

一般閲覧者はアカウントを必要としない。

以下の経路から掲示物を閲覧する。

* 公開掲示板の招待リンク
* 公開掲示板の掲示物に付与されたQRコード

一般閲覧者は非公開掲示板を閲覧できない。

一般閲覧者は管理機能へアクセスできない。


| 掲示物の登録・編集・差し替え・撤去 | ○ | ○ |

| 公開設定の変更 | ○ | × |

# 6. 掲示物ステータス

掲示物は以下のステータスを持つ。

```text
draft
published
removed
```

基本的な状態遷移は以下とする。

```text
draft
  ↓
published
  ↓
removed
```

期限切れ状態はステータスとして保存しない。

期限切れかどうかは `expiresAt` と現在時刻から算出する。

```text
status === "published"
AND
expiresAt <= now
```

* サムネイル
* 掲示開始日時
* 掲示終了日時

必要に応じて以下を保持してよい。

* 説明文
* 外部URL

以下の情報は扱わない。

* カテゴリ
* 対象者

# 8. 原本のアップロード

掲示物の原本は以下のいずれかの形式とする。

* PDF（`application/pdf`）
* 画像（`image/jpeg`、`image/png`、`image/webp`）

SVGは許可しない（ファイル内にスクリプトを書けるため）。許可する形式とサイズの上限は、アップロードURLを発行するユースケースで検証する。

アプリケーションサーバーを経由せず、クライアントからストレージへ直接アップロードする。

アップロードフローは以下とする。

```text
Client
  ↓
presigned PUT URL取得（キーはサーバーが `pending/` 以下に乱数で決める）
  ↓
ストレージへ直接PUT
  ↓
アップロード完了
  ↓
Post登録を依頼
  ↓
サーバーがファイルの中身の形式を確認
  ↓
確認を通ったファイルを正式な場所へ移し、Post登録
```

### アップロードしたファイルの確認

署名付き URL が縛るのは、申告された種類（`Content-Type`）とサイズだけで、ファイルの中身は確かめない。`application/pdf` と申告すれば、中身が何でも保存できてしまう。

そのため、Post を登録する前に、サーバーがファイルの先頭のバイト（マジックバイト）を読み、許可する形式であり、申告した種類と一致することを確かめる。原本とサムネイルの両方に行う。クライアントが申告した種類や、サムネイルが作れたことを、この確認の代わりにしない。

確認に通らなければ Post を登録せず、ファイルを消す。

署名付き URL は有効期限内なら同じキーへの上書きを許すので、確認したあとに別の中身へ差し替えられる余地がある。そのため、確認したときのオブジェクトの世代（`generation`）を覚えておき、正式な場所へ移すときはその世代を条件にする（`ifSourceGenerationMatch`）。移せたときだけ Post を登録する。移せなかった（差し替えられた）ときは登録しない。

### 登録されなかったファイルの後始末

アップロードしたまま Post の登録まで進まなかったファイル（画面を閉じた、確認で弾いたが消し損ねたなど）が、バケットに残り続けないようにする。

* アップロード先は `pending/` 以下とし、Post の登録時に、確認を通ったファイルだけを正式な場所へ移す
* `pending/` には、1日で自動削除するライフサイクルを設定する

ストレージ上のファイルは原則として非公開とする。

原本を取得する際には署名付きGET URLを発行する。

ストレージへは Google Cloud Storage の API で接続し、接続先（バケット・エンドポイント）は環境変数で切り替える。

* 本番: Google Cloud Storage（`@google-cloud/storage`。鍵ファイルを持たず、Cloud Run のサービスアカウントで署名する）
* ローカル開発: `fake-gcs-server`（`compose.yaml` で起動）。署名を検証しないので、正常系の確認用
* CI: 上記に加え、開発用の GCP プロジェクトの実バケットに対して、署名の強制（サイズ・種類・有効期限・署名なし）を確かめる結合テストを実行する

当初は本番を Cloudflare R2、ローカルを MinIO としていた。デプロイ先を GCP にしたため本番を Cloud Storage に変え、接続も S3 互換 API ではなく Google の SDK にした（期限のない HMAC キーを持たずに済むため）。ローカルのエミュレーターは署名を検証しないため、異常系の確認は CI から実バケットに対して行う。

アプリケーションコードは接続先の違いを意識しない。

# 9. サムネイル

原本のアップロード時に、ブラウザ側でサムネイルを生成する。

```text
PDF                        画像
 ↓                          ↓
pdf.js                     ブラウザで縮小
 ↓                          ↓
1ページ目を描画して画像化      ↓
 └──────────┬──────────────┘
            ↓
      ストレージへアップロード
```

PDFの描画には `pdf.js` を使用する。画像は原本を縮小する。

サーバー側ではPDFレンダリングも画像処理も行わない。

10MB程度の原本を実用上問題のない速度で処理できることを目安とする。

# 10. 掲示期間

掲示物には以下の日時を設定する。

```text
publishFrom
expiresAt
```

一般閲覧者向けの掲示板に表示される条件は以下とする。

```text
status === "published"
AND
publishFrom <= now
AND
expiresAt > now
```

掲示開始前の掲示物は公開しない。

掲示終了日時を過ぎた掲示物も公開しない。

---

# 11. 期限切れ判定

掲示終了日時を過ぎた掲示物は、自動的に一般掲示板から除外する。

期限到来時に `Post.status` を更新する必要はない。

期限切れ状態は以下で判定する。

```text
status === "published"
AND
expiresAt <= now
```

期限切れ掲示物は以下の扱いとする。

* 一般掲示板には表示しない
* 撤去タスクに表示する
* 管理用台帳には表示する

---

# 12. 掲示板ボード

掲示板ボードでは、現在公開中の掲示物を画像形式で一覧表示する。

レイアウトには masonry を使用する。

異なるアスペクト比の掲示物が混在していても、表示が破綻しないこと。

各掲示物を選択すると掲示物詳細画面へ遷移する。

表示対象は公開条件を満たす掲示物のみとする。

## 12.1 メンバー向け表示

掲示板メンバーは `/boards/{boardId}` から掲示板ボードを閲覧する。表示する掲示物は一般閲覧者向けと同じとする。

メンバー向け画面（`/boards` 配下）には、サイドバーに以下を配置する。

* 所属する掲示板の一覧（所属した日時の新しい順。表示中の掲示板を強調する）
* 掲示板作成画面への導線

サイドバーの掲示板を選択すると、その掲示板の掲示板ボードへ遷移する。狭い画面ではサイドバーを折りたたみ、メニューから開けるようにする。

メンバー向け表示では、ヘッダーに以下を配置する。

* 掲示物登録・撤去タスク・台帳への導線
* 招待リンクの表示・コピー（公開掲示板のみ）
* 招待リンクの再発行（公開掲示板のみ、admin のみ）
* 掲示板設定・メンバー管理への導線（admin のみ）

一般閲覧者向け表示（`/b/{inviteToken}`）には管理用の導線を表示しない。

# 14. QRコード

公開中の掲示物にはQRコードを発行できる。

QRコードの遷移先は掲示物詳細画面とする。

例:

```text
/posts/{publicId}
```

公開URLには、原則として内部DB IDを直接利用しない。

外部公開用の識別子を使用する。

# 15. 撤去タスク

撤去タスク画面では、期限を過ぎているにもかかわらず、まだ撤去されていない掲示物を一覧表示する。

表示条件は以下とする。

```text
status === "published"
AND
expiresAt <= now
```

撤去タスクには最低限以下を表示する。

* 掲示物サムネイル
* タイトル
* 掲示板
* 掲示終了日時
* 期限超過時間

ユーザーは、実際の掲示物を撤去した後に「撤去済み」として登録できる。

撤去完了時には以下を更新する。

```text
status = "removed"
removedAt = now
```

必要に応じて撤去したユーザーを記録する。

```text
removedBy
```

撤去済みの掲示物は撤去タスク一覧に表示しない。

---

# 16. 掲示物台帳

掲示物一覧 / 台帳では、現在および過去の掲示物を確認できる。

最低限以下の状態を識別して表示する。

* 下書き
* 公開中
* 掲示開始前
* 期限切れ / 撤去待ち
* 撤去済み

表示状態は `Post.status` のみではなく、日時も考慮して算出する。

例:

```text
status = "draft"
→ 下書き
```

```text
status = "published"
publishFrom > now
→ 掲示開始前
```

```text
status = "published"
publishFrom <= now
expiresAt > now
→ 公開中
```

```text
status = "published"
expiresAt <= now
→ 期限切れ / 撤去待ち
```

```text
status = "removed"
→ 撤去済み
```

# 17. 掲示物編集

登録済みの掲示物について以下を変更できる。

* タイトル
* 原本ファイル
* 掲示開始日時
* 掲示終了日時
* 説明文
* 外部URL

原本を変更した場合は、新しいファイルをストレージへアップロードする。

原本の変更時には対応するサムネイルも再生成する。

差し替え処理中に既存掲示物が参照不能になる状態を作らないこと。

---

# 18. 認証

認証には Google OAuth を使用する。

独自のメールアドレス・パスワード認証は提供しない。

ログイン画面には原則としてGoogleログインボタンのみを表示する。

```text
Googleでログイン
```

ログイン後の遷移先は以下とする。

* 最後に開いた掲示板があり、現在も所属している場合: その掲示板（`/boards/{boardId}`）
* それ以外で所属する掲示板がある場合: 所属した日時（`BoardMember.createdAt`）が最も新しい掲示板（サイドバーの先頭）
* 所属する掲示板がない場合: 掲示板作成画面（`/boards/new`）

最後に開いた掲示板は、メンバー向け掲示板ボードが表示されたときに Cookie へ掲示板 ID を保存して記録する。ブラウザ単位で記録し、アカウントには紐づけない。

Cookie の値は利用者が書き換えられるため、遷移先を決める際は必ず所属を確認し、所属していない掲示板 ID は無視する。

# 19. 認可

掲示板単位のアクセス権限を管理する。

管理系処理を実行する際は、対象ユーザーがその掲示板にアクセス可能か確認する。

認可ロジックは各画面・APIへ分散させず、共通処理へ集約する。

例:

```ts
checkBoardAccess(...)
```

少なくとも以下の処理では認可を行う。

* 掲示物登録
* 掲示物編集
* 掲示物差し替え
* 掲示物撤去
* 台帳閲覧
* 撤去タスク閲覧
* 招待リンク表示・再発行
* 掲示板の編集・削除
* メンバーの一覧・追加・ロール変更・削除
* 公開設定の変更
* 非公開掲示板の掲示板ボード・掲示物詳細の閲覧

認可では所属の有無に加えて、操作に必要なロールを確認する（「5. ロール」）。

掲示板の作成では、ログイン済みであることのみを確認する。

Board IDを知っているだけでは管理機能へアクセスできないこと。

---

# 20. 招待リンク

掲示板ごとに閲覧用の招待リンクを発行できる。

一般閲覧者はGoogleログインを行わずに招待リンクから掲示板へアクセスできる。

招待情報は `InviteToken` で管理する。

URL例:

```text
/b/{inviteToken}
```

InviteTokenは推測困難なランダム値とする。

招待リンクで閲覧できるのは公開掲示板のみとする。

有効なInviteTokenを持つ閲覧者は、その公開掲示板の公開中掲示物を閲覧できる。

招待リンクは掲示板作成時に発行する。掲示板ごとに有効な招待リンクは1つとする。

メンバーは掲示板ボードのメンバー向け表示から招待リンクを表示・コピーできる。

admin は招待リンクを再発行できる。再発行すると以前のリンクは無効になる。

---

# 21. 掲示板管理

ログインユーザーは掲示板作成画面から掲示板を作成できる。

掲示板作成時には、以下を1つのトランザクションで行う。

* `Board` を作成する（公開設定を含む）
* 作成者を admin として `BoardMember` に登録する
* `InviteToken` を発行する

admin は掲示板設定画面で以下を行える。

* 掲示板名の編集
* 公開設定の変更
* 掲示板の削除

掲示物（撤去済みを含む）が1件でもある掲示板は削除できない。台帳の履歴を失わないためである。

掲示板を削除する際は、その掲示板の `BoardMember` と `InviteToken` も削除する。

---

# 22. 公開設定

掲示板は公開（public）または非公開（private）のいずれかとし、`Board.isPublic` で管理する。

閲覧できる範囲は以下とする。

| 経路 | 公開掲示板 | 非公開掲示板 |
| -- | -- | -- |
| メンバー向け掲示板ボード `/boards/{boardId}` | メンバーのみ | メンバーのみ |
| 招待リンク `/b/{inviteToken}` | 誰でも（ログイン不要） | 閲覧不可 |
| 掲示物詳細 `/posts/{publicId}` | 誰でも（ログイン不要） | メンバーのみ |

非公開掲示板の掲示物詳細は以下の扱いとする。

* 未ログインの場合: ログイン画面へ遷移し、ログイン後に元のURLへ戻る
* ログイン済みで所属していない場合: 存在しない掲示物と同じ表示にする

非公開掲示板の招待リンクは、存在しない招待リンクと同じ表示にする。

公開設定は掲示板作成時に選択する。既定は非公開とする。

admin は掲示板設定画面から公開設定を変更できる。変更は即時に反映する。

非公開から公開に戻すと、発行済みの招待リンクは再び有効になる。以前のリンクを無効にしたい場合は招待リンクを再発行する。

公開掲示板の一覧・検索は提供しない。

閲覧可否の判定は共通化し、画面ごとに再実装しない。

---

# 23. メンバー管理

admin はメンバー管理画面で以下を行える。

* メンバー一覧の閲覧
* メンバーの追加
* ロールの変更
* メンバーの削除

メンバーの追加では、Googleアカウントのメールアドレスとロールを指定する。

追加できるのは、一度以上ログインしたことがあるユーザーのみとする。未登録のメールアドレスが指定された場合はエラーとし、先にログインしてもらうよう案内する。

同じユーザーを同じ掲示板へ重複して登録しない。

掲示板には常に1人以上の admin が存在すること。最後の admin のロール変更・削除はできない。

```ts
  post.status === "published" &&
  post.publishFrom <= now &&
```

```ts
  post.status === "published" &&
  post.expiresAt <= now
```


# 33. セキュリティ要件

* ストレージ上の原本およびサムネイルは原則として非公開とする
* ファイル取得には署名付きURLを利用する
* 管理APIでは認証・認可を確認する
* Board IDのみを利用した権限回避を防止する
* InviteTokenは推測困難な値とする
* 一般閲覧者から管理APIへアクセスできないこと
* 招待リンクの再発行・掲示板設定・メンバー管理は admin のみ実行できること
* 非公開掲示板の掲示物・ファイルの署名付きURLは、メンバーであることを確認してから発行すること
* ユーザー入力値はサーバー側でも検証する
* ログに、セッションや招待リンクのトークン、秘密の値（`BETTER_AUTH_SECRET` など）、SQL のパラメータ（検索や登録に使った値）を出さない
* 画面に出すエラーメッセージは、想定内の失敗の理由（`reason`）に応じた文言か、決まった一般的な文言だけとし、内部のエラーの内容を表示しない
* レスポンスにセキュリティ用の HTTP ヘッダー（クリックジャッキング対策など）を付ける
* ログインなどの認証 API に、回数の制限をかける

# 34. パフォーマンス要件

原本ファイルはアプリケーションサーバーを経由せず、クライアントからストレージへ直接アップロードする。

```text
Browser
 ↓
ストレージ
```

以下の構成は避ける。

```text
Browser
 ↓
Application Server
 ↓
ストレージ
```

10MB程度の原本について、通常利用に支障のないアップロード・サムネイル生成が行えること。

掲示板一覧では、必要以上に原本を取得せず、サムネイルを利用する。

署名付きURLの発行と、ストレージへの問い合わせ回数については以下とする（ステップ5で実測してから調整する）。

* 署名付きURLの発行は、鍵を持たない方式のため1本につきIAMへの通信が1回発生する。一覧では並行に発行し、順番待ちにしない
* ブラウザのキャッシュを効かせるため、同じファイルには一定時間同じ署名付きURLを返す（URLが毎回変わるとキャッシュが効かない）。あわせてオブジェクトに `Cache-Control` を設定する
* 上記のURLのキャッシュは、必要と分かってから入れる（先に作らない）
* 共有キャッシュを導入する場合は、キャッシュ参照より先に閲覧権限を確認し、キャッシュキーに掲示板・利用者などの認可コンテキストを含める。認可コンテキストを分離できない場合は共有キャッシュを使わない

# 36. 実装上の原則

実装は可能な限り単純な構成を優先する。

構成は `AGENTS.md` に記載のオニオンアーキテクチャ（機能モジュール × レイヤー）で統一する。

トランザクション境界はユースケース（application）が決める。ユースケースは `UnitOfWork` インターフェース（`src/shared/domain/unit-of-work.ts`）を受け取り、その `run` の中でリポジトリを使う。リポジトリのメソッドは内部でトランザクションを張らない。読み取りだけのユースケースは `UnitOfWork` を使わず、リポジトリを直接受け取ってよい。

明確な必要性がない限り、以下のような構成を導入しない。

* CQRS
* Event Sourcing
* 将来機能のためだけのInterface
* 不要な状態管理
* 不要なenum

必要なドメインロジックについては、画面コンポーネントへ直接埋め込まず共通化する。

## 38.6 台帳

1. 下書きを確認できる
2. 掲示開始前の掲示物を確認できる
3. 公開中の掲示物を確認できる
4. 期限切れ・撤去待ちの掲示物を確認できる
5. 撤去済み掲示物を確認できる
6. 掲示期間を確認できる
7. 掲示物を編集できる
8. 原本を差し替えられる

## 38.7 掲示板管理

1. ログインユーザーが掲示板を作成できる
2. 作成者がその掲示板の admin になる

5. admin が掲示物のない掲示板を削除できる
6. 掲示物がある掲示板は削除できない
7. poster は掲示板の編集・削除ができない

## 38.8 メンバー管理

1. admin がメールアドレスとロールを指定してメンバーを追加できる
2. 未登録のメールアドレスは追加できない
3. 登録済みのメンバーを重複して追加できない
4. admin がロールを変更できる
5. admin がメンバーを削除できる
6. 最後の admin はロール変更・削除できない
7. poster はメンバー管理を行えない
8. 所属していないユーザーは、掲示板の管理画面・管理処理にアクセスできない

---

## 38.9 ログイン後の遷移

1. 最後に開いた掲示板に現在も所属している場合、その掲示板へ遷移する
2. 最後に開いた掲示板の記録がない、または所属していない場合、所属した日時が最も新しい掲示板へ遷移する
3. 所属する掲示板がない場合、掲示板作成画面へ遷移する
4. Cookie を書き換えて所属していない掲示板 ID にしても、その掲示板へは遷移しない

6. サイドバーから別の掲示板へ移動できる
7. 所属していない掲示板はサイドバーに表示されない

2. admin が招待リンクを再発行できる
3. 再発行後は以前のリンクで掲示板を開けない
4. poster は招待リンクを再発行できない

1. 掲示板作成時に公開・非公開を選択できる（既定は非公開）
2. admin が公開設定を変更できる
3. poster は公開設定を変更できない

5. 非公開掲示板の掲示物詳細は、未ログインの場合ログイン画面へ遷移し、ログイン後に元の掲示物詳細へ戻る
6. 非公開掲示板の掲示物詳細は、所属していないユーザーには表示されない
7. 非公開掲示板の掲示物詳細は、メンバーが閲覧できる
8. 公開掲示板の一覧・検索画面は存在しない

# 40. 最重要要件

本システムでは、以下の一連の処理が常に成立することを最優先とする。

```text
掲示物を登録する
       ↓
掲示板へ公開する
       ↓
掲示期限が到来する
       ↓
一般閲覧から自動的に消える
       ↓
撤去タスクへ表示される
       ↓
物理掲示物を撤去する
       ↓
撤去済みとして記録する
       ↓
履歴として台帳に残る
```

このライフサイクルを損なう設計・実装を行わないこと。
